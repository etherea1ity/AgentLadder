## The Chapter In One Sentence

Chapter 3 does not add more business rules to the loop. It makes the agent runtime observable: the core loop still owns model calls, tool execution, and stopping; hooks own lifecycle placements; trace records public events; and the frontend renders the same public event stream through three separate surfaces.

![Klara Chapter 3 Hooks and Trace](../assets/ch03-hooks-and-trace.svg)

## The Three Surfaces

### 1. Top Thinking Trigger

The main user path gets a lightweight GPT-like entry:

```text
active:     mini Klara + Thinking... + timer
completed:  mini Klara + Thought for X >
```

It does not expand into a tool chain. It does not show raw payloads or developer trace. Clicking the text body does nothing; only the right chevron / button opens the Activity Drawer.

Code:

```text
apps/web/src/components/klara/KlaraThinkingBlock.tsx
apps/web/src/components/ChatWorkspace.tsx
apps/web/src/styles/klara.css
```

### 2. Activity Drawer

The Activity Drawer is a public activity summary, not private model thinking. It has two sections:

```text
Klara thinking  -> 2-5 public activity items generated by the narrator from the completed trace
Agent activity  -> activity_item_upserted events projected from real runtime events
```

Even when the main model has no stream and no thinking tokens, Activity still works because it is grounded in runtime events: model call started, web_search returned candidate sources, web_fetch returned page text, final answer writing started, and so on.

Every activity item must include `evidence_event_ids` and may only cite public events that actually happened. It must not expose raw tool arguments, full URLs, full observations, raw payloads, secrets, file contents, or chain-of-thought.


### 3. Developer Debug

Developer Debug is for teaching and engineering inspection. It is collapsed by default:

```text
Developer debug · 38 events · 3 tools
```

When expanded, it can show:

- LLM rounds: turn index, model, duration, input/output/total tokens, token source.
- Tools: tool name, status, duration, arguments preview, observation preview.
- Trace: event count, trace saved, event_id, created_at, event_type.
- Raw payloads: only inside Developer Debug `<details>`.

If duration or token fields are missing, the UI renders `unknown` instead of inventing numbers.

Code:

```text

apps/web/src/styles/klara.css
```

## 3.1 Why Tool Chains Do Not Belong In Thinking

Tool chains are important, but they are not user-visible thinking.

If the top thinking area expands into `Searched web / Opened page / Answered`, two things go wrong:

- Users may read it as the model's actual private reasoning.
- Debug information competes with the final answer.

So Chapter 3 draws a clean product boundary:

```text
Top Thinking Trigger -> a lightweight entry that says Klara is/was thinking
Activity Drawer      -> public, evidence-backed activity summary
Developer Debug      -> engineering trace, tool cards, payloads, and metrics
```

Public activity may be shown. Hidden reasoning is not shown. Engineering debug does not pretend to be thinking.

## 3.2 Public Activity Item Contract

Chapter 3 introduces this activity item shape:

```json
{
  "id": "act_...",
  "title": "Looking up public information",
  "body": "Klara is checking external sources before answering.",
  "status": "running",
  "kind": "evidence",
  "source": "runtime_event",
  "evidence_event_ids": ["evt_..."],
  "confidence": 0.9
}
```

Allowed `kind` values:

```text
orientation
evidence
tool_activity
composition
finalization
```

Allowed `source` values:

```text
runtime_event
narrator_model
provider_reasoning
fallback
```

This chapter's main path uses `runtime_event` and `narrator_model`. `provider_reasoning` is reserved for future provider reasoning streams; it does not mean Klara currently displays raw chain-of-thought.

## 3.3 Runtime Activity Projection

We do not change the core loop or hook protocol. Runtime activity is derived in the API projection layer from existing events.

Examples:

```text
llm_call_started
-> activity_item_upserted: "Reading the request"

tool_call_started web_search
-> activity_item_upserted: "Looking up public information"

tool_call_completed web_fetch
-> activity_item_upserted: "Source material reviewed"

answer_streaming_started
-> activity_item_upserted: "Writing the answer"
```

These items describe public actions only. They do not carry raw arguments, full URLs, full observations, or raw payloads.

Tests:

```text
tests/apps/api/test_run_event_projector.py
tests/apps/api/test_thinking_summary.py
```

## 3.4 Narrator Summary

The narrator model only writes the completed public activity summary:

```text
input:  complete public run events
output: 2-5 activity items plus fallback text
never:  final answer, chat history, assistant message mutation
```

It must output strict JSON:

```json
{
  "text": "Klara prepared the run, checked public evidence, and wrote the final answer.",
  "items": [
    {
      "title": "Checked public evidence",
      "body": "Klara searched public sources before composing the answer.",
      "kind": "evidence",
      "evidence_event_ids": ["evt_123"],
      "confidence": 0.8
    }
  ]
}
```

The validator rejects or downgrades unsafe summaries:

- Item count must be 2-5.
- Title/body must be non-empty.
- Body must stay short.
- `evidence_event_ids` must exist.
- It cannot claim Klara searched, opened, read, verified, ran, edited, or tested anything unless public events prove it.
- Narrator failure must not affect the main answer.
- If narrator is unavailable, Klara emits `thinking_summary_completed has_summary=false` and does not invent fake items.

## 3.5 Hooks And Trace Remain The Runtime Spine

The UI refactor does not change the core hooks/trace shape:

```text
KlaraLoop
-> public KlaraEvent
-> HookManager
-> JsonlTraceHook
-> RunEventProjector
-> SSE / Activity Drawer / Developer Debug
```

Hook placements are still small lifecycle boundaries:

```text
UserPromptSubmit -> user request enters runtime
PreToolUse       -> before one tool call executes
PostToolUse      -> after a tool observation exists
Stop             -> before the run completes
```

Chapter 3 does not turn hooks into semantic correctors, domain guards, intent routers, or search-rule engines.

## 3.6 Why This Is Real

This Activity layer is not a fake "thinking deeply" ticker:

- Every activity item has `evidence_event_ids`.
- Runtime items are projected from real RunEvents.
- Narrator items must cite existing events.
- No narrator means no fake summary.
- Activity does not reveal raw chain-of-thought.
- Developer Debug and public Activity are separate surfaces.

That gives Klara two mature product patterns at once:

- A GPT-like collapsed `Thought for X >` entry.
- A Claude Code / Codex-like observable workstream.

Klara keeps public activity separate from raw debug so engineering logs do not masquerade as thinking.

## 3.7 Quick Experience

Start:

```powershell
.\scripts\dev.ps1
```

Open:

```text
http://127.0.0.1:5123
```

Try three prompts:

```text
What time is it in Shanghai now?
```

Expected: the model may call `current_time`; the top row only shows `Thinking...` / `Thought for X`; Activity shows public work; Developer Debug shows the tool event.

```text
Search for the latest World Cup schedule.
```

Expected: if the model uses web tools, Activity summarizes public actions only; Developer Debug shows `web_search` / `web_fetch` details. The runtime does not patch the answer with hardcoded World Cup rules.

```text
Generate an image of Klara.
```

Expected: the model may call `image_generate`, the answer can render the image, and Activity/Debug remain separate.

## 3.8 What This Chapter Does Not Do

Chapter 3 does not add:

- raw chain-of-thought display
- intent router
- domain guard
- search keyword rules
- source ranker
- grounding verifier
- complex permission system
- memory or context compression

Those topics belong to later chapters. This chapter first locks the boundaries between loop, hooks, trace, Activity, and Debug.
