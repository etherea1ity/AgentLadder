# Agent Ladder v0.1 Webapp Specification

This reference is the authoritative contract for implementing the v0.1 Agent Ladder full-stack webapp. Keep v0.1 minimal but structurally correct.

## 1. Product identity

- Project: Agent Ladder
- Subtitle: From Prompt to Policy
- Branch/theme: v0.1 Minimal Agent
- Chapter goal: From LLM API Call to Minimal Agent
- Product idea: A quiet workspace for learning how an agent runs.
- Chinese mental model: 一张安静的学习桌；左边是会话历史，中间是问答，右边是当前 run 的旁注。

## 2. v0.1 scope

### Must do

1. User asks one question.
2. Backend creates session/message/run.
3. Agent core creates `AskState`.
4. `MinimalAgent` calls the configured LLM client.
5. Agent core creates `AnswerState`.
6. Agent core creates `RunLog`.
7. Agent core/backend saves a JSONL trace.
8. Frontend displays conversation and streaming answer.
9. Frontend shows safe visible activity in `ThinkingInlineBar`.
10. User clicks an assistant message `ThinkingInlineBar` to open the right Run Margin for that run only.
11. User can rename and delete sessions; delete must call backend and update storage.
12. Refresh restores non-deleted sessions from local JSONL storage.

### Must not do

No RAG, source cards, citations, evidence pack, memory resolver, selected sources, research report, MCP servers, eval dashboard, RL reward view, auth, billing, database migration, multi-user collaboration, file upload, complex settings, graph visualization, or raw chain-of-thought display.

## 4. Visual and UX direction

### Desired aesthetic

quiet, paper-like, ink, margin notes, minimal, philosophical, editorial, warm neutral, low contrast, state-aware.

### Forbidden aesthetic

neon, cyber, heavy gradient, enterprise dashboard, 3D SaaS illustration, dark heavy sidebar, purple/blue gradient buttons, too many cards, too many icons.

### UI language

All UI text must be English.

### Visual reference description

Use the supplied image as the visual target:

- Left warm-paper sidebar with ladder mark, Agent Ladder, subtitle, version pill, New Chat, Today, Earlier, and quiet footer.
- Main area with top path bar, centered message column, generous whitespace, user message, assistant message, calm ThinkingInlineBar, and bottom input.
- Right Run Margin opened only after selecting a run; it shows Current Run, status, summary, activity timeline, run log, and collapsed/optional JSON actions.


### Typography

- UI font: system sans or Inter if available.
- Hero/title may use Georgia or `ui-serif`.
- Answer text should be readable, calm, and not tiny.
- Run Margin text one size smaller than main chat.

### Spacing

- Sidebar: 248-264px desktop.
- Message column: max-width about 760px.
- Run Margin: 340-360px desktop.
- Generous vertical spacing.
- Hairline borders; minimal shadows.

### Motion

Use motion only to convey state:

- Thinking dot breathing: opacity 0.45 → 1 → 0.45, scale 0.96 → 1.04 → 0.96, duration ~1.4s.
- Run Margin slide/fade: 160-220ms.
- Event row fade-in.
- Streaming caret.

Avoid spinners, bouncing loaders, big transitions, and 3D movement.

## 5. Layout behavior

### Default: two columns

`Left Sidebar | Main Chat Workspace`

Right Run Margin is not rendered and occupies no space.

### Opened: selected-run three-column behavior

When `selectedRunId` exists and `runMarginOpen = true`:

`Left Sidebar | Main Chat Workspace | Run Margin`

Run Margin only shows the selected run. It must never show all runs or global metrics.

### Open triggers

Only these open Run Margin:

1. Click an assistant message `ThinkingInlineBar`.
2. Click assistant message `Details` action.
3. URL query contains a valid `run_id`, e.g. `?run=run_123`.

Sending a message must not open Run Margin.

### Responsive behavior

- Desktop large >= 1280px: layout push; sidebar fixed; Run Margin fixed 340-360px; main shrinks smoothly but message column stays centered and max-width ~760px.
- Desktop medium 1024-1279px: Run Margin as non-modal overlay side sheet with border/shadow, no backdrop, ESC and X close.
- Tablet/mobile < 900px: Run Margin as full-height drawer or bottom sheet; close returns to chat; ESC/close/swipe down where feasible.

## 6. Sidebar rules

Sidebar includes only:

- Brand: ladder mark, Agent Ladder, From Prompt to Policy.
- Version: v0.1, Minimal Agent.
- New Chat.
- Conversation groups: Today, Earlier.
- Optional small footer/avatar/settings icon, with no settings page needed for v0.1.

Conversation item fields:

- title
- updated time
- active indicator
- more menu only on hover/focus

More menu:

- Rename
- Delete

### New Chat

Use lazy session creation:

1. Click New Chat.
2. Close Run Margin.
3. Set `activeSessionId = null` or draft.
4. Clear chat workspace.
5. Show empty home.
6. Focus input.
7. Do not call `POST /api/sessions` until the user sends the first message.

### Title generation

Do not use LLM-generated titles. Generate title from first user message:

- first 6-10 English words
- remove line breaks
- truncate over 40 characters
- fallback `Untitled`
- allow rename later

### Sorting/grouping

`GET /api/sessions` returns non-deleted sessions. Frontend sorts `updated_at` descending. Today goes under Today; everything else goes under Earlier.

### Delete behavior

Delete must call backend.

Interaction:

- lightweight confirmation popover, not a large modal.
- Title: `Delete this conversation?`
- Body: `This removes it from the sidebar and conversation view.`
- Buttons: `Cancel` / `Delete`

On confirm:

1. `DELETE /api/sessions/{session_id}`.
2. Backend soft-deletes session and cancels active run if any.
3. Frontend removes session from list.
4. If deleted session is active: `activeSessionId = null`, `selectedRunId = null`, `runMarginOpen = false`, empty home.
5. If running run existed: backend emits `run_cancelled`; UI no longer shows that session.

Deletion strategy: append tombstone with `deleted_at`; hide messages/runs/events from normal GET; keep trace as local learning audit.

## 7. Chat Workspace

### Empty home

Show only:

- Ladder mark.
- `From Prompt to Policy`.
- `A question becomes a trace.`
- Input placeholder: `Ask your first question...`
- Subtle hint: `v0.1 Minimal Agent · Ask → Answer → Trace`

Do not add large flow diagrams, quick-start cards, or complex hero illustrations.

### Active chat

User message:

- label `You`
- content
- optional timestamp

Assistant message:

- label `Agent Ladder`
- ThinkingInlineBar
- content
- message actions after completed

### Input

- fixed near bottom
- aligned with message column
- placeholder: `Ask anything...`
- Enter sends
- Shift+Enter creates newline
- running state: send button becomes Stop
- disable or stop if another run active in same session
- attachment button absent or disabled, not visually advertised as available

### Send flow

1. If no active session, `POST /api/sessions`.
2. Optimistically insert user message.
3. Optimistically insert assistant placeholder.
4. Assistant shows ThinkingInlineBar: `Queued · Preparing the run...`.
5. `POST /api/runs`.
6. Open `GET /api/runs/{run_id}/events/stream` SSE.
7. `answer_delta` appends to assistant content.

Do not open Run Margin automatically.

### Stop flow

Reserve `POST /api/runs/{run_id}/cancel`.

If backend can cancel LLM call: interrupt stream, emit `run_cancelled`, assistant status `cancelled`, bar says `Stopped · Partial answer saved`.

If backend cannot truly cancel: mark `cancelled_requested`, stop frontend consumption, do not write later backend output into current visible assistant content, and document as known limitation.

## 8. ThinkingInlineBar

ThinkingInlineBar is a button/disclosure trigger, not decoration. It never shows raw chain-of-thought.

### Position

Inside every assistant message:

1. ThinkingInlineBar
2. AssistantContent
3. MessageActions

### Status text

- queued: `○ Queued · Preparing the run...`
- thinking: `◌ Thinking · Understanding your question...`
- streaming: `◌ Writing · Answer is streaming...`
- completed: `✓ Completed · 2.4s · View trace`
- failed: `! Failed · Open details`
- cancelled: `Stopped · Partial answer saved`

### Click logic

Clicking a ThinkingInlineBar opens or switches Run Margin:

```text
selectedRunId = message.run_id
runMarginOpen = true
```

If the same bar is clicked again while open, keep it open. X closes. This avoids accidental close.

Clicking another assistant message switches selected run.

### Accessibility

Use a real `button` with:

- `aria-expanded={runMarginOpen && selectedRunId === run_id}`
- `aria-controls="run-margin-panel"`
- `aria-label="Open run trace for this answer"`
- Enter/Space support
- visible but subtle focus ring

## 9. Run Margin

### Render rules

- No `selectedRunId`: do not render, no layout space.
- Valid `selectedRunId`: render selected run.
- Close sets `selectedRunId = null`, `runMarginOpen = false`, focus returns to triggering ThinkingInlineBar.

### Running view

For queued/thinking/streaming, show:

- Current Run
- Status: Thinking/Writing
- live phrase: `Understanding your question...` or `Answer is streaming...`
- activity: run_created, thinking_started, llm_call_started, answer_streaming aggregate
- live elapsed time, streamed chars, model if known
- token fields absent or `—`

Do not show final summary, token table, Copy JSON, full trace, or completed log during running.

### Completed view

Show:

- Completed + duration
- Summary: `This run created an AskState, called the LLM, produced an AnswerState, and saved a JSONL trace.`
- Activity Timeline: run_created, thinking_started, llm_call_started, answer_streaming, llm_call_completed, run_completed
- Run Log: run_id, session_id, model, latency_ms, prompt_tokens, completion_tokens, total_tokens, trace_saved, created_at, completed_at
- Trace: View JSON toggle and Copy JSON; JSON collapsed by default

### Failed view

Show:

- Failed
- short reason
- last event/failed stage
- error code/message/stage
- Retry, Copy error, Close

### Cancelled view

Show:

- Stopped
- Partial answer saved
- timeline: run_created, thinking_started, run_cancelled
- run log: run_id, session_id, elapsed_ms

### Timeline rules

Timeline rows only for:

- run_created
- thinking_started
- llm_call_started
- answer_streaming_started or aggregate `answer_streaming · N chars streamed`
- llm_call_completed
- run_completed
- run_failed
- run_cancelled

Never render every `answer_delta` as a timeline row.

## 10. Frontend state model

Use TypeScript and maintain one source of truth.

```ts
type RunStatus = "queued" | "thinking" | "streaming" | "completed" | "failed" | "cancelled";
type MessageStatus = "idle" | "running" | "completed" | "failed" | "cancelled";

type Session = {
  session_id: string;
  title: string;
  created_at: string;
  updated_at: string;
  deleted_at?: string | null;
  message_ids: string[];
};

type Message = {
  message_id: string;
  session_id: string;
  role: "user" | "assistant";
  content: string;
  run_id?: string;
  status?: MessageStatus;
  created_at: string;
  updated_at?: string;
};

type Run = {
  run_id: string;
  session_id: string;
  user_message_id: string;
  assistant_message_id: string;
  status: RunStatus;
  model?: string;
  started_at?: string;
  completed_at?: string;
  latency_ms?: number;
  prompt_tokens?: number;
  completion_tokens?: number;
  total_tokens?: number;
  trace_saved?: boolean;
  error?: { code?: string; message: string; stage?: string };
  events: RunEvent[];
  live?: { elapsed_ms?: number; streamed_chars: number; current_label: string };
};

type RunEventType =
  | "run_created"
  | "thinking_started"
  | "llm_call_started"
  | "answer_delta"
  | "answer_streaming_started"
  | "llm_call_completed"
  | "run_completed"
  | "run_failed"
  | "run_cancelled";

type RunEvent = {
  event_id: string;
  run_id: string;
  event_type: RunEventType;
  message: string;
  payload?: Record<string, unknown>;
  created_at: string;
};

type UIState = {
  activeSessionId: string | null;
  selectedRunId: string | null;
  runMarginOpen: boolean;
  sidebarCollapsed: boolean;
  inputFocused: boolean;
  activeSseRunId: string | null;
};
```

Core bindings:

- `assistant_message.run_id = run.run_id`
- ThinkingInlineBar reads run status/live/log.
- RunMargin reads selected run.
- Session switch clears selected run and closes margin.

## 11. Backend API

Use FastAPI or equivalent, but the planned default is FastAPI.

### Sessions

`POST /api/sessions`

Request `{}`. Response:

```json
{"session_id":"sess_...","title":"Untitled","created_at":"...","updated_at":"..."}
```

`GET /api/sessions`

Response:

```json
{"sessions":[{"session_id":"sess_...","title":"What is an AI Agent?","created_at":"...","updated_at":"..."}]}
```

`GET /api/sessions/{session_id}`

Response:

```json
{"session":{},"messages":[],"runs":[]}
```

`PATCH /api/sessions/{session_id}`

Request `{ "title": "New title" }`.

`DELETE /api/sessions/{session_id}`

Soft delete, hide from list/detail, cancel active run, return:

```json
{"session_id":"sess_...","deleted":true,"deleted_at":"..."}
```

### Runs

`POST /api/runs`

Request:

```json
{"session_id":"sess_...","question":"What is an AI Agent?"}
```

Response:

```json
{"run_id":"run_...","session_id":"sess_...","user_message_id":"msg_user_...","assistant_message_id":"msg_assistant_...","status":"queued","events_url":"/api/runs/run_.../events/stream"}
```

`GET /api/runs/{run_id}` returns run, events, and trace.

`GET /api/runs/{run_id}/events` returns historical events.

`GET /api/runs/{run_id}/events/stream` streams SSE.

`POST /api/runs/{run_id}/cancel` returns cancelled or cancellation requested status.

### SSE contract

Use SSE because v0.1 only needs server-to-client push and browser `EventSource` is simpler than WebSocket.

Each SSE event includes event name and JSON data matching `RunEvent`.

Required event examples:

```text
event: run_created
data: {"event_id":"evt_1","run_id":"run_1","event_type":"run_created","message":"Run created.","payload":{},"created_at":"..."}

event: thinking_started
data: {"event_id":"evt_2","run_id":"run_1","event_type":"thinking_started","message":"Understanding your question...","payload":{},"created_at":"..."}

event: llm_call_started
data: {"event_id":"evt_3","run_id":"run_1","event_type":"llm_call_started","message":"Calling the language model...","payload":{"model":"qwen3.6-plus"},"created_at":"..."}

event: answer_delta
data: {"event_id":"evt_4","run_id":"run_1","event_type":"answer_delta","message":"","payload":{"delta":"An AI Agent is "},"created_at":"..."}

event: llm_call_completed
data: {"event_id":"evt_5","run_id":"run_1","event_type":"llm_call_completed","message":"LLM call completed.","payload":{"completion_tokens":126},"created_at":"..."}

event: run_completed
data: {"event_id":"evt_6","run_id":"run_1","event_type":"run_completed","message":"Run completed.","payload":{"latency_ms":2400,"prompt_tokens":53,"completion_tokens":126,"total_tokens":179,"trace_saved":true},"created_at":"..."}

event: run_failed
data: {"event_id":"evt_7","run_id":"run_1","event_type":"run_failed","message":"Run failed.","payload":{"error":{"code":"missing_api_key","message":"DASHSCOPE_API_KEY is missing","stage":"llm_call_started"}},"created_at":"..."}
```

Frontend rules:

- `answer_delta` appends to assistant message content.
- `answer_delta` does not become individual timeline rows.
- `run_completed` updates run log and terminal state.
- `run_failed` shows failed UI.
- If SSE closes before terminal state, reconcile with `GET /api/runs/{run_id}`.

## 12. Agent core / run lifecycle

Core must be UI-agnostic.

Recommended lifecycle:

1. create `AskState`
2. emit `run_created`
3. emit `thinking_started`
4. emit `llm_call_started`
5. stream LLM deltas
6. build `AnswerState`
7. build `RunLog`
8. save JSONL trace
9. emit `llm_call_completed`
10. emit `run_completed`

Current v0.1 should prefer `AskState`, `AnswerState`, `RunLog`, and `RunEvent`. If ActionState/ObservationState or calculator already exist, do not surface them in UI; if they do not exist, do not add tool UI for v0.1.

Real provider: DashScope/OpenAI-compatible. Test provider/mock may be added for tests only.

Never persist or display raw model chain-of-thought/reasoning_content. Use safe status summaries only.

## 13. Storage / persistence

Use local JSONL for v0.1.

Files:

```text
data/app/sessions.jsonl
data/app/messages.jsonl
data/app/runs.jsonl
data/app/run_events.jsonl
data/traces/runs.jsonl
```

Principles:

- session/message/run use app storage.
- trace uses trace storage.
- run_events restore timeline and SSE replay.
- append-only is preferred for teaching/audit.
- GET APIs replay JSONL into current state at startup or request time.

Delete strategy:

- append tombstone event with `deleted_at`.
- list/detail hide deleted sessions.
- session detail for deleted session returns 404 or deleted status consistently.
- messages/runs/events for deleted sessions hidden from ordinary UI APIs.
- traces remain as local learning audit.
- document this as local learning mode deletion.

Future migration notes must map JSONL to SQLite/Postgres tables.

Optional dev script: `scripts/dev/clear_local_data.py` to clear local JSONL files.

## 17. Acceptance criteria

### Product / UX

- Sidebar simple: name/version/New Chat/Today/Earlier only.
- Home page English-only and minimal.
- No complex cards on home.
- Run Margin hidden by default.
- ThinkingInlineBar opens Run Margin.
- Run Margin shows only selected run.
- Session switch closes Run Margin.
- Delete active session returns to empty home.

### Thinking / Run

- queued/thinking/streaming/completed/failed/cancelled states supported.
- Motion calm and informative.
- Completed view shows summary/token/log; running view does not.
- Failed view shows stage and retry/copy error.
- No raw chain-of-thought.

### Backend

- `POST /api/runs` creates run and message pair.
- SSE pushes run events and answer deltas.
- `GET /api/sessions` restores sessions.
- `DELETE /api/sessions/{id}` hides session in frontend and backend.
- JSONL trace saved.
- Cancel supported or limitation documented with safe frontend behavior.

### Architecture

- frontend/backend/core separated.
- UI does not call LLM.
- backend does not hardcode UI component logic.
- core does not depend on FastAPI/React.
- event schema can extend to v0.2 sources/citations/tool_calls/evidence.

### Tests

At minimum:

- unit tests for contracts
- unit tests for JSONL append/replay/delete
- unit tests for run lifecycle
- API tests for sessions/runs/delete
- SSE integration test
- frontend component tests for ThinkingInlineBar states
- e2e test for ask → stream → click thinking → Run Margin → completed → delete → refresh
